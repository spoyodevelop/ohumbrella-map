# 리팩터링 체크리스트

작은 책임 분리부터 진행하고, 외부 계약이나 DB를 바꾸는 작업은 별도 단계로 다룬다.
각 단계는 `npm run check`와 `npm run build`가 통과하는 크기로 커밋한다.

## 완료한 기반 작업

- [x] 클라이언트의 HTTP 요청을 `fetchJson`으로 통일한다.
- [x] 날씨 데이터 로딩을 `useWeatherData`로 분리한다.
- [x] React Compiler를 Vite 빌드에 연결한다.
- [x] 클라이언트의 넓은 범위에서 사용되는 상태 변수 이름을 정리한다.
- [x] 서버를 포함한 TypeScript 검사 명령을 구성한다.
- [x] 지도 hover 상태와 사전 로딩을 제거하고 SVG 기본 툴팁을 사용한다.
- [x] 드래그·휠·핀치 중 지도 transform을 React 렌더와 분리한다.

## 0. 현재 변경 정리

- [x] `server/api.ts`의 설명을 되풀이하던 주석 제거분을 검토한다.
- [x] 체크리스트 변경과 주석 정리를 별도 커밋으로 나눈다.

## 3. 서버 진입점과 라우트 정리

- [x] `server/index.ts`에서 DB를 초기화한 뒤 워커 스케줄을 시작한다.

## 4. 날씨 데이터 계약 정리

현재 날씨와 시도 통계의 API 응답 계약은 클라이언트와 서버가 공유한다. 내부 날씨 타입과 DB 경계는 남아 있다.

- [x] 현재 날씨와 시도 통계의 공유 API 응답 계약을 만든다.
- [x] 날씨 저장 레코드, 조회 행, API 응답 타입을 구분한다.
- [ ] 기상청 원본 `PTY`와 내부 `precipitationType`을 분리한다.
- [ ] 기존 DB의 `pty` 컬럼과 내부 타입 사이에 명시적인 변환 경계를 둔다.
- [ ] 중복된 `pop`과 `kmaPop`의 역할을 정리한다.
- [x] API의 `isRaining`을 boolean으로 바꾸고 DB 저장 값은 숫자로 유지한다.
- [ ] `pop`, `rn1`, `tmp`, `sky`는 외부·DB 경계에서만 유지하고 내부 도메인 이름을 정한다.
- [ ] 클라이언트의 도달 불가능한 PTY 분기를 제거하거나 새 내부 타입에 맞춘다.

## 5. DB 스키마와 마이그레이션

API 계약 정리와 분리해서 진행한다. 기존 데이터 보존 방법을 정하기 전에는 컬럼을 바꾸지 않는다.

- [ ] 현재 스키마 생성과 마이그레이션의 책임이 섞여 있는지 점검한다.
- [ ] `hourly_weather`와 관측·예보 테이블의 중복 책임을 문서화한다.
- [ ] 컬럼 이름 변경이 필요한지 확정한다.
- [ ] 변경한다면 기존 로컬 SQLite와 Turso 모두를 위한 마이그레이션 절차를 만든다.
- [ ] 뷰와 backfill이 재실행되어도 안전한지 확인한다.

## 이름과 주석 원칙

- 공개 경계와 넓은 범위의 변수는 역할이 드러나는 이름을 사용한다.
- 짧은 지역 범위의 관용적인 이름은 억지로 늘리지 않는다.
- 코드 내용을 되풀이하는 주석은 이름이나 구조를 개선한 뒤 제거한다.
- 외부 API 규칙, 정책, 선택 이유를 설명하는 주석은 유지한다.
- 이름 변경만으로 여러 파일을 흔들 경우 얻는 이점이 분명한지 먼저 확인한다.

## 현재 범위에서 하지 않는 것

- 자동 polling은 도입하지 않는다. 사용자가 필요할 때 새로고침한다.
- 모든 API 응답에 Zod 같은 런타임 검증을 일괄 도입하지 않는다.
- `fetchJson<T>`의 타입 단언은 신뢰하는 내부 API 경계에서 유지한다.
- DB 컬럼 변경과 대규모 이름 변경을 작은 모듈 분리 작업에 섞지 않는다.
- 단순히 파일 줄 수를 줄이기 위한 추상화는 만들지 않는다.
